## Exploration: Port Git Playground (vanilla JS + dc-runtime) to Vite + React + TypeScript

### Current State

Two source files in `design-handoff/`, no framework, no build step:

**`git-engine.js`** (536 lines, single IIFE, `window.GitEngine`) — a pure, synchronous Git simulator.
- **State shape** (`vacio()`): `{v, inited, files, index, commits, order, branches, colorOf, nColors, laneOf, lanes, detLane, tags, head:{type:'branch'|'detached', name|hash}, prev, stash[], reflog[], remote:{branches,known}, tracking, upstream, op, seq, tm}`. `commits[hash] = {hash,n,msg,parents[],tree,author,t,lane,x,local,dy?,copyOf?,cherryOf?,revertOf?}`. Fully JSON-serializable (uses `cl()` = `JSON.parse(JSON.stringify())` for deep clone).
- **Commands** (dispatch table `GIT`, called via `ejecutar(estado, "git ...")`): `init, status, add, restore, rm, mv, commit (-m/-a/-am/--amend), log (--oneline/--graph/--all), show, diff (--staged), branch (-d/-D/-m/-a), switch (-c/-d), checkout (-b/--/-- <file>), tag (-d), merge (--no-ff/--abort), rebase (--continue/--abort/-i→unsupported), cherry-pick, revert, reset (--soft/--mixed/--hard), stash (push/pop/apply/drop/list/show/clear), reflog, remote (-v, fixed single "origin"), push (-u/-f), fetch, pull (--rebase), clean (-n/-f), help, version`. Plus shell-level: `ls, cat, touch, echo (> / >>), rm, mv, clear, pwd, cd (stub), mkdir (fails — no folders), edit (returns `accion:{tipo:'editar',archivo}`)`. Unknown/unsupported git subcommands have curated "not supported" messages (`NO` table) and typo suggestion via Levenshtein (`cercano`/`lev`).
- **Top-level engine API**: `ejecutar(estado,input)→{estado,salida[],eventos[],accion,error}`, `ejemplo()` (seeds demo repo + fake remote), `vacio()`, `escribir(estado,file,text)`, `resolver(estado,file,modo:'mia'|'suya'|'ambas')`, `companero(estado)` (simulates teammate pushing to origin), `explicar(eventos,estado)→{icon,tone,text}|null` (one human-readable synthesizer per event type, Spanish, with inline `` `code` `` spans), `layout(estado)→{pos,nodes,edges,links,labels,phantom,rpos,rnodes,redges,rlabels,rbox,stash,bbox}` (full SVG geometry), `estadoArchivos`, `headHash`, `treeOf`, `cambiosCommit`, `infoRama`, `refsDe`, `curName`, `colorRama`, `short`, `resolve`, `tokens`, `completar(estado,linea)→{last,pool}` (tab-completion), constants `PALETA`, `DX`, `DY`.
- **Event types** emitted (`r.ev(type,data)` inside command handlers, plus auto-diffed via `diffEventos(prev,next,r)` comparing two states): `repo-init, branch-created, branch-deleted, branch-renamed, switched, detached, tag-created, tag-deleted, commit-created, commit-amended, merge-commit, cherry-picked, reverted, fast-forward, up-to-date, merge-conflict, rebase-done, commits-copied, op-aborted, reset, stash-pushed, stash-popped, stash-dropped, push-sent, fetch-received, pull-done, remote-commit, file-restored, conflict-resolved, error` + diff-derived: `file-created, file-deleted, file-modified, file-staged, file-unstaged, head-moved, head-detached, ref-moved, commits-orphaned, commits-restored`.
- **Output markup**: lines use `\x01kind\x02text\x03` segments (kind ∈ `m,g,r,y,w,e,h,cy,bold,c:<hexcolor>`), parsed client-side by `parseLine()`/`segColor()` into colored spans. This encoding is the wire format between engine and UI and must be preserved.
- **Tricky internals**:
  - `hashStr(str)` — custom 5-round FNV/imul hash producing 40-hex-char ids. Must be ported byte-exact (`Math.imul`, `>>>` unsigned shifts) for internal self-consistency; it is NOT real-git-compatible, just deterministic given the same `(msg,parents,tree,author,seq)` input — `seq` is a repo-local counter, not wall-clock, so hashes ARE deterministic across runs given identical command sequences. The non-deterministic field is `t` (commit timestamp, `Date.now()` fallback) and `fecha()`'s `toLocaleString('es-ES',...)` (locale/timezone dependent) — both must be frozen/mocked in parity tests.
  - Lanes/colors (`laneFor`, `ensureColor`, `colorRama`) are assignment-order-dependent (first-seen branch name gets next lane/color index) — relies on JS object key insertion-order guarantees; safe to port 1:1 but risky if migrated to `Map`/`Set` with different iteration assumptions.
  - `op` state machine (`s.op = {kind:'merge'|'rebase'|'cherry-pick'|'revert', ...}`) carries conflict data (`conflicts[]`, `data{file:{ours,theirs}}`, `origW/origI` snapshots for `--abort`, `pairs[]` for rebase commit remapping) — this is the most stateful/imperative part of the engine and needs careful typed modeling (discriminated union per `op.kind`).
  - Remote simulation: single fixed `origin` with `remote.branches` (server truth), `remote.known` (commit-reachability cache for push diffing), `tracking` (local cache of last-seen origin refs = `origin/<branch>`), `upstream` (local branch → tracked remote branch name). `fetch`/`push`/`pull`/`companero()` all mutate this independently of local `branches`.
  - 3-way merge (`fusionar3`, `fusionLineas`, `hunks`, `diffTxt`) implements a real LCS-diff + hunk-based auto-merge with conflict detection — this is the most algorithmically dense piece and the highest-value target for exhaustive unit tests.

**`Git Playground.dc.html`** (574 lines) — a `dc-runtime` (`support.js`, reference-only, NOT ported) template (`<x-dc>`, `sc-if`, `sc-for`, `{{ }}` bindings, `style-hover`) wrapping one big class component (`class Component extends DCLogic`, lines 220–570).
- UI regions: pan/zoom SVG canvas (grid background), floating "Files" strip (working dir / staging / last-commit columns, collapsible, mobile variant), top-right action bar (teammate-commit button, theme toggle, reset-repo dropdown w/ 2 confirm options), toast stack (top-center, 2-max, 4s auto-dismiss), hover/focus tooltip (commit/branch/HEAD/track/tag/stash/phantom-conflict, computed world→screen position), merge/rebase/cherry-pick/revert conflict resolver panel (per-file ours/theirs diff + mine/theirs/both/edit actions) + collapsed pill, inline file editor modal (textarea, Ctrl+Enter save / Esc cancel), camera controls (zoom in/out/fit/center-on-HEAD), draggable/resizable/minimizable/maximizable terminal window (history ↑/↓, Tab autocomplete, colored prompt reflecting branch+op state, mobile bottom-sheet layout), empty-state overlay, an absolutely-positioned overlay `div` used purely as an imperative DOM animation layer (`fly()` chip animations between arbitrary element rects), and an `aria-live` region.
- Script responsibilities: camera pan/zoom/pinch (no inertia — direct `cam={x,y,k}` imperatively applied via `transform` on a ref'd `<g>`, never through React state, to avoid re-render thrash), "safe area" rectangle computation (avoids overlapping the terminal) used for auto-fit/auto-center, a **choreography pipeline** (`mkPlan(events,prev,next)` → diff of two `layout()` outputs produces a `plan` object with per-node birth delays/origins, label move paths, camera moves; `choreo()` executes it) driving WAAPI (`Element.animate`) through **ref-callback identity guards** (`el.__born === plan` pattern) so each DOM node only animates once per plan version, cross-DOM "fly" chip animations (`getBoundingClientRect` + `animate()` + manual cleanup), toast queue (opacity/transform lifecycle + timers), tooltip positioning, terminal drag/resize via raw `pointermove`/`pointerup` listeners, `localStorage` persistence (key `gitpg:v1`: `{repo, theme, hist}`), theme toggle (`data-theme` attribute + CSS custom properties, dark default), mobile layout branching, and an undocumented debug API `window.GitPlayground = {estado, ejecutar, motor, cargar}`.

### Approaches

**1. State management — `useReducer` vs external store (zustand)**
1. **`useReducer` for repo/domain state; plain hooks+refs for ephemeral UI** (camera, terminal geometry, toasts, tooltip) — mirrors the original's `apply(engine.ejecutar(...))` pattern almost 1:1.
   - Pros: zero new dependency; reducer is a thin, 100%-pure wrapper around `engine.ejecutar`, trivially testable without React; matches `rerender-use-ref-transient-values` guidance (camera/choreography stay in refs, not state, avoiding re-render storms during animation).
   - Cons: ephemeral UI slices (terminal geometry needed by camera's `safe()` calc) must be shared via context or prop-threading.
   - Effort: Low.
2. **zustand store(s) for everything** (repo slice + UI slice + camera slice) with selector subscriptions.
   - Pros: avoids context re-render fan-out; easy outside-React access (useful for a `window.GitPlayground`-equivalent debug API); clean slice separation.
   - Cons: new dependency; doesn't remove the need for imperative refs for WAAPI/camera anyway; adds abstraction not justified for a single-page, non-deeply-nested tree in v1.
   - Effort: Low-Medium.

**2. Animation — keep WAAPI (imperative, ref-callback) vs framer-motion**
1. **Keep WAAPI**, 1:1 port of `mkPlan`/`choreo`/`fly`/ref-callback-with-`__born`-guard pattern, now as React `ref` callbacks.
   - Pros: this *is* how the original achieves perf and the exact fly/draw-on/stagger choreography; lowest risk for full parity in slice 1; no new dependency; consistent with `rendering-animate-svg-wrapper` and `advanced-event-handler-refs`.
   - Cons: imperative code is harder to read/test than declarative; must guard ref callbacks against firing redundantly on every React render (stable callback + identity check on `plan`, same as original's `el.__born===P`).
   - Effort: Medium (mechanical but large surface: ~15 animation call sites).
2. **framer-motion/motion for React** for some/all animation.
   - Pros: nicer DX for simple enter/exit (toasts, labels).
   - Cons: cannot cleanly express cross-arbitrary-DOM-rect "fly" chips, diff-based staggered birth delays computed from two `layout()` snapshots, or `strokeDasharray` path draw-on without still writing custom imperative code — net result is likely both WAAPI *and* framer-motion, i.e. added bundle weight without removing complexity. High rewrite/parity risk for v1.
   - Effort: High.

**3. SVG graph rendering — per-node React components vs single memoized layer**
1. **Single memoized rendering layer** — a pure function/`useMemo`'d component mirroring `buildGraph(repo, plan)`, still keyed per node/edge/label hash for React reconciliation, with the same `ref` callback hooks for WAAPI.
   - Pros: preserves the plan-identity animation contract exactly; avoids rewriting the choreography timing model; `buildGraph()` is independently unit-testable as a pure function (input: repo+plan, output: element/geometry tree) even without React; good perf (`layout()` is O(n), recomputed only on repo/plan change, matching original's `_gr/_gv` cache keys).
   - Cons: less idiomatic "many small components" React style.
   - Effort: Medium.
2. **Per-node components** (`<CommitNode>`, `<Edge>`, `<Label>`, each `React.memo`'d).
   - Pros: idiomatic, each visual state unit-testable in isolation.
   - Cons: fights the original's architecture — ref-callback timing/`__born` guards become harder to coordinate across independently-memoized components; risk of subtly breaking the stagger/choreography parity goal.
   - Effort: Medium-High.

### Recommendation

- State: `useReducer` wrapping a ported `engine.ejecutar`-equivalent reducer for repo/domain state (testable without React); dedicated hooks (`useCamera`, `useChoreography`, `useToasts`, `usePersistence`, `useTerminalWindow`) hold ephemeral UI/animation state in refs, not reducer state — no new state-management dependency for v1.
- Animation: keep WAAPI with the same ref-callback + plan-identity pattern, ported mechanically. Do not introduce framer-motion for v1; revisit only for isolated, simple cases later.
- Graph rendering: single memoized layer mirroring `buildGraph()`, implemented as a pure, independently-testable function, with `key`s per node/edge/label and ref callbacks for WAAPI hookups.
- Proposed engine module split: `state.ts` (types + `vacio`), `hash.ts` (`hashStr`), `refs.ts` (`resolve`/`resolveOr`/Levenshtein), `diff.ts` (`diffTxt`/`hunks`/`fusionLineas`/`fusionar3`/`diffArboles`), `commands/` (one file per git subcommand group: files, commit-history, branches, integrate (merge/rebase/cherry-pick/revert), undo (reset/stash/reflog), remote), `layout.ts`, `explain.ts`, `completion.ts`, `engine.ts` (barrel: `ejecutar`/`ejemplo`/`vacio`/`escribir`/`resolver`/`companero`). Each gets typed `RepoState`, `GitEvent` (discriminated union), `OpState` (discriminated union per `op.kind`), `CommandResult`.
- Proposed React tree: `GitPlaygroundProvider` (repo reducer + engine context) → `CanvasPane` (pan/zoom handlers + `GraphSVG` single-layer renderer) + `FilesStrip` (Working/Staging/Commit lists) + `TopRightActions` (Teammate/Theme/Reset) + `ToastStack` + `Tooltip` (portal) + `ConflictResolver`/`ConflictPill` + `FileEditorModal` + `CameraControls` + `TerminalWindow` (header drag/resize/min/max, output list, prompt/input w/ autocomplete) + `EmptyStateOverlay` + `FlyOverlayLayer` (imperative, ref-only, not reconciled) + `LiveRegion`.

### Testing Strategy

- **Golden parity harness (highest value, Vitest)**: load the original `design-handoff/git-engine.js` in a Node/jsdom test via a small shim (`globalThis.window = globalThis` before `require`/dynamic import of the raw file, since it's an IIFE that assigns `window.GitEngine`), then run a corpus of command scripts (init/add/commit sequences, branch/switch/merge incl. conflicts, rebase incl. conflicts, cherry-pick, revert, reset soft/mixed/hard, stash push/pop/apply/drop, tag, push/fetch/pull incl. divergence, `companero()`, `clean`, unknown-command suggestions) through both the original engine and the new TS port from identical seed states, and deep-equal: `salida` (incl. markup), `eventos`, `error`, final `estado` minus non-deterministic fields (`commits[].t`, anything derived from `Date.now()`/locale) — freeze via `vi.useFakeTimers()`/fixed `TZ`/`LANG` in CI.
- **Unit tests per module**: `resolve`/`resolveOr` (HEAD~n, HEAD^n, short-hash ambiguity), `fusionar3`/`fusionLineas`/`hunks` (3-way merge + conflict detection, including partial-overlap edge cases), `procesarRebase` linearization, `reset` modes, `stash` push/pop/apply semantics incl. untracked-file handling, `layout()` geometry snapshots (bbox/pos/edges for representative repo shapes), `explicar()` event→message mapping (one assertion per event type), `completar()` pools, `hashStr` self-consistency.
- **Explicitly out of golden-test scope**: WAAPI choreography/timing (UI layer) — cover instead with React Testing Library interaction tests (typing a command updates output; clicking Fit/Head calls the camera function; conflict-resolver buttons call `resolver` with the right mode) with `Element.prototype.animate` stubbed via a `vitest.setup.ts` polyfill (fake `Animation` with callable `onfinish`) so choreography code doesn't throw under jsdom.

### Risks

- Timestamp/locale nondeterminism (`Date.now()`, `toLocaleString('es-ES', ...)`) must be frozen for stable golden-parity tests across CI machines/timezones.
- `hashStr` must be ported bit-exact (`Math.imul`, unsigned shifts) — subtle precision drift breaks hash self-consistency (not correctness, but breaks golden diffs and any snapshot tests keyed on hash strings).
- Lane/color assignment is iteration-order-dependent on plain-object key order — safe in TS if kept as plain objects/Maps with insertion order preserved; risky if refactored carelessly.
- The `op` state machine (merge/rebase/cherry-pick/revert conflict + abort/continue flows) is the most complex typed-state modeling work; recommend a discriminated union with exhaustive switch handling to avoid silent `any`-typed op fields.
- Choreography (`mkPlan`/`choreo`) is tightly coupled to live DOM measurement (`getBoundingClientRect`, `getTotalLength`) and hand-tuned millisecond heuristics — hardest-to-automate-test UI work; plan for manual/visual QA rather than full unit coverage, and isolate it as its own task slice.
- `dc-runtime` → JSX translation (`sc-if`/`sc-for`/`{{ }}`/`style-hover`/`ref="{{ x }}"`) across ~350 lines of markup is mechanical but error-prone; do it region-by-region with a checklist, not as one diff.
- Mobile layout math (`safe()`, `camBottom`, bottom-sheet sizing) is interdependent across `mobile`/`term`/`vh` state — must be one cohesive hook, not fragmented, to avoid regressions.
- `window.GitPlayground` debug API and the `gitpg:v1` localStorage schema are undocumented but load-bearing contracts (future lessons layer depends on `estado`/`cargar` shape) — preserve exactly.
- **Size/PR-budget risk**: this is a full-parity port of ~535 (engine) + ~350 (UI markup) + ~350 (UI script) dense lines into an estimated 4000–6000+ TS/TSX/CSS/test lines. This far exceeds the 400-changed-line PR review budget. Strongly recommend chaining into multiple deliverable slices for `sdd-tasks`, e.g.: (1) scaffold + engine core + golden-parity harness, (2) remaining engine modules (layout/explain/completion/merge) + unit tests, (3) React shell + reducer + terminal (no animation), (4) SVG graph rendering + camera, (5) choreography/WAAPI animations, (6) files-strip/toasts/tooltip/conflict-resolver/editor, (7) theme/persistence/mobile polish. Flag this explicitly to the tasks-phase review-workload guard.
