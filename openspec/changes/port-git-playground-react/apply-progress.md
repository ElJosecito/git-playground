## Review fixes

Three confirmed judgment-day review findings fixed (STRICT TDD: RED test per fix, then GREEN), surgically — no refactors beyond what each fix required:

1. **Back-to-back commands dropped the first command's `after()` choreography.** `src/app/useGitPlayground.ts` — `applyResult` called `choreo.prepare()` once per command (correct), but the `useLayoutEffect` keyed on `state.transition?.id` only read `state.transition`, which `playgroundReducer` only ever keeps as the LATEST transition. Two synchronous `run()` calls inside one `act()`/event-handler tick (e.g. two `window.GitPlayground.ejecutar()` calls back to back) batch into a single React commit, so the effect fired once — only the second command's `after()` ran, silently dropping the first command's toast/aria-live/animation choreography. Root cause: React's `useReducer` batching collapses multiple dispatches into one committed render, but the effect's dependency (`transition.id`) only exposes the LAST dispatch's payload, with no record of the ones in between. **Fix**: added a ref-held queue (`pendingAfterRef`) in `useGitPlayground` — `applyResult` pushes `{res, prev, next}` for every command synchronously (before dispatch), and the `useLayoutEffect` drains the full queue in order on each commit, calling `choreo.after()` once per queued command (skipping entries with a null `prev`, same guard as before) and dispatching `liveSet` for each. `playgroundReducer.ts` was NOT touched — `state.transition` still works exactly as before for its existing callers. Test: `src/app/__tests__/useGitPlayground.test.ts` — "drains after() for EVERY applied command, in order, even when two run() calls batch into one commit" (fake choreo spy, two `run()` calls in one `act()`, asserts `after` called 2× with each command's own prev/next pair, chained correctly).
2. **`GraphLayer`'s `memo()` was defeated by two unstable object props.** (a) `src/hooks/useChoreography.ts:673` returned a fresh `refs: { node, rnode, edge, label, pulse, stash }` object literal every render, even though all six callbacks were already individually stable (`useCallback`) — wrapped in `useMemo(..., [node, rnode, edge, label, pulse, stash])`. (b) `src/components/PlaygroundShell.tsx:163-166` built `graphHandlers` as a fresh `{ onHover, onUnhover }` literal every render — wrapped in `useMemo(..., [tooltip.hover, tooltip.unhover])`. Tests: `src/hooks/__tests__/useChoreography.test.ts` ("`refs` stays referentially stable across rerenders") and new file `src/components/__tests__/PlaygroundShell.graphMemo.test.tsx` (mocks `GraphLayer` with a `memo()`-wrapped render-counting stub, types into the terminal input, asserts the mock only rendered once).
3. **`usePersistence()` returned a fresh `{ initial, save }` wrapper object every render.** `src/hooks/usePersistence.ts:76` — `initial` (`useState`) and `save` (`useCallback`) were each individually stable, but the object wrapping them was rebuilt every render. `PlaygroundShell`'s `persist` callback lists `[persistence]` as its dep, so the unstable wrapper cascaded into a new `persist` → new `persistenceDeps` → new `run`/`loadRepo` out of `useGitPlayground` on every render, re-running the `installDebugApi` effect (deps `[run, loadRepo]`) and reinstalling `window.GitPlayground` on every unrelated rerender. **Fix**: wrapped the return in `useMemo(() => ({ initial, save }), [initial, save])`. Tests: `src/hooks/__tests__/usePersistence.test.ts` — "returns a referentially stable result object across unrelated rerenders" (direct identity check) and "does not reinstall window.GitPlayground across an unrelated rerender" (composes `usePersistence` + a `[persistence]`-dependent `persist` callback + `useGitPlayground`, isolated from `useChoreography`'s own unrelated object-identity behavior, which was out of scope for this fix).
